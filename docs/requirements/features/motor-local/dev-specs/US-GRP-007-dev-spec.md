# Dev Spec — US-GRP-007: sesiones de Claude Code detectadas

Plano compacto (AADD ligero) de [US-GRP-007](../user-stories/US-GRP-007-sesiones-claude-code.md). Sobre el observador y el historial de US-GRP-002, añade el **detector de sesiones** de [ADR-GRP-012](../../../../architecture/decisions/ADR-GRP-012-deteccion-sesiones-claude-code.md) y fija el **modelo de sesión** (estados, origen y presencia) que reutiliza US-GRP-009.

**Qué entrega**: con el motor observando, cada Claude Code lanzado en un worktree observado aparece como sesión **detectada** en estado "Activo" (`raptor status`, `raptor sessions` y `session.state` en el stream). Pasa a "Inactivo" tras 5 minutos sin actividad en su worktree, vuelve a "Activo" con un cambio y queda "Terminado" cuando su proceso desaparece. Un commit que Claude Code hace en su worktree tiene como actor `Claude Code (detectado)` cuando la ascendencia de procesos (S3) lo prueba; si no, queda "sin atribuir". El motor no instala hooks, no toca la configuración de Git y no escribe nada fuera de su perfil.

## 4. Riesgos y pendientes

- **Carrera de S3** (aceptada en ADR-GRP-012): un `git commit -m` muy corto puede terminar antes de la muestra; el commit queda "sin atribuir", nunca mal atribuido. El escenario 1 usa un commit con hook para ser determinista; la tasa real la mide SPIKE-GRP-001 (§ 5).
- **Riesgo residual de atribución humano → Claude Code**: un `git` de Claude Code (p. ej. `git status`) vivo en el mismo worktree cuando el desarrollador hace un commit cuyo `git` ya terminó, o que se lanzó desde un IDE con su cwd fuera del repo (GitKraken, VS Code), atribuiría ese commit a Claude Code. Se mitiga con "empezó antes del aviso", el cwd en el worktree del evento y la colocación por el ancestro; lo mide la suite guionizada del spike. Si aparece, se aplica la vía de fracaso de SPIKE-GRP-001.
- **Instalación por npm** (`node …/cli.js`): sin detectar hasta la lectura acotada de argv[1] (D4).
- **Windows**: sin lectura de procesos ni detección; `detection_available: false`. **Linux**: lectura por `/proc` probada solo con las pruebas de `crates/core` del CI; los escenarios de punta a punta usan `script` y corren en macOS. Pendiente: etapa de validación multiplataforma.
- **Interfaces preparadas**: `SessionView` y `sessions.list` para el registro y la confirmación (US-GRP-009) y la corrección (US-GRP-010); `SessionConfig.inactivity` para US-GRP-013; `HookEvidence` para Guardrails; `process_cwd` en macOS para el registro (US-GRP-009); `ObserverHooks` para la atribución por archivo de US-GRP-008, que también se queda el adaptador de transcripts (D2).

## 5. Medición de la precisión en dogfooding (SPIKE-GRP-001)

SPIKE-GRP-001 se valida con esta historia, con el motor real en lugar del prototipo aislado que preveía ADR-GRP-012 (enmienda del ADR). **Es una validación parcial: S1 + S3.** S2a y S2b siguen abiertas hasta que US-GRP-008 conecte el adaptador de transcripts.

- **Montaje**: `raptor` compilado en release desde `main`, observando el repo `gitRaptor` de Rene en macOS, con sus worktrees de Orca. Claude Code instalado con el instalador nativo o Homebrew (binario `claude`); se anota el método, porque con npm la medición no vale (D4).
- **Duración**: **2 semanas y al menos 50 sesiones reales**. Si a las 2 semanas no se llega a 50, se amplía; si no se puede ampliar, el resultado se declara no significativo.
- **Datos**: cada día, `raptor sessions --all --json` y `raptor events --all --json`, guardados fuera del repo. Solo llevan metadatos: agente, worktree, horas, estados y actor; nunca contenido (NFR-03). El log del daemon aporta `s3_evidence` con su resultado y los contadores `s3_cwd_unreadable` y `s3_placed_by_ancestor`.
- **Verdad de referencia**:
  - **Sesiones**: Rene marca cada sesión como correcta o incorrecta (worktree equivocado, duplicada, no era de Claude Code) y añade las que faltaron.
  - **Commits**: el trailer `Co-Authored-By: Claude` que Claude Code añade a sus commits hace de árbitro automático, comparado fuera del motor sobre la exportación; Rene revisa solo las discrepancias y marca aparte los commits hechos desde GitKraken u otro IDE (hueco declarado de D8).
- **Suite guionizada en macOS** (dentro de esta validación): humano y Claude Code en el mismo worktree y en otro; Claude Code que modifica otro directorio (R3); dos sesiones en un worktree; cierre forzado; suspensión del equipo. Mide el criterio "0 commits humanos atribuidos a Claude Code".
- **Métricas**:
  - **Precisión de sesiones (Q9)** = sesiones correctas / (sesiones detectadas + sesiones que faltaron). Meta ≥ 90%.
  - **Humano → Claude Code** = commits del desarrollador con actor Claude Code. Meta: **0** (BR-EDGE-004).
  - **Carreras perdidas de S3** = commits de Claude Code "sin atribuir" / commits de Claude Code, para decidir si S4 (Guardrails) o S5 hacen falta.
  - **Transiciones**: sesiones que no pasaron a "Inactivo" tras 5 min sin actividad o que no volvieron a "Activo"; sesiones que no pasaron a "Terminado" al cerrar Claude Code; sesión nueva tras `--resume` o `--continue`.
- **Entregables pendientes del spike**: la respuesta sobre la TTY de la shell de Claude Code y la comprobación de privacidad del adaptador de transcripts (esta, con US-GRP-008).
- **Resultado**: `research/SPIKE-GRP-001-resultados.md`. Si la precisión queda por debajo del 90% o algún commit del desarrollador se atribuye a Claude Code, se aplica la vía de fracaso del spike (replantear ADR-GRP-012 con S5 y escalar a Rene).

## 7. Enmienda S4 (2026-10-07): la resolución del hook de Guardrails atribuye el evento

**Hallazgo del dogfooding (2026-10-07)**: con los hooks de Guardrails instalados, el hook resolvió que los commits rápidos los hacía Claude Code (y los bloqueó por política), pero los mismos commits rápidos que sí entraron salieron "sin atribuir" en `raptor events`: S3 mira el árbol de procesos **después** del commit y pierde la carrera con los `git` cortos (§ 4). El hook corre **dentro** del `git`, así que su ascendencia no tiene carrera. Es la señal **S4** que ADR-GRP-012 ya contempla como evidencia positiva y opcional; `HookEvidence` era su costura (§ 4, "Interfaces preparadas") y hasta hoy solo tenía `NoHooks`.

Todas son **Decisión del orquestador (2026-10-07), validada por el Arquitecto** (aprobada con ajustes; columna de la derecha, A) **y aprobada por el coordinador con ajustes** (C). La enmienda correspondiente de ADR-GRP-012 es la del 2026-10-07.

| # | Decisión | Ajuste |
|---|---|---|
| S4-1 | **Dónde nace la señal**: en `guard.evaluate` de un `reference-transaction` `prepared` (`Operation::RefTransaction`, hook obligatorio de las plantillas 1 y 2), cuando la decisión es `allow` (la transacción va a aplicarse). Es el único punto del hook que conoce **ref y oid nuevo**, y corre para toda rama local gobernada (`refs/heads/*`). `commit-msg` no sirve: el commit aún no existe y no hay oid | |
| S4-2 | **Quién**: `requester::resolve(peer, checks, None)` **tal cual** (sin marcas del ejecutor, así nunca espera el registro de un hijo del daemon: el hook de un `git` del ejecutor no espera nada, ADR-GRD-003). Solo cuenta un resultado `via: ancestry` con `Requester::Agent` detectado: la pista del multiplexor (regla 5 del solicitante) y el ejecutor **no** generan S4, porque no prueban que ese `git` descienda de esa sesión. `guardrails/actor.rs` y `requester::resolve` no cambian | |
| S4-3 | **Qué se guarda** (`detect::HookClaims`, en memoria, compartido por el canal y el detector): `{repo_id, worktree (cwd canónico del cliente del hook, que Git fija en la raíz del worktree), refname, oid nuevo, session_id, git (pid, inicio), t (monotónico)}` por cada `RefUpdate` con valor nuevo `Oid`. Tope FIFO de 256 y caducidad de 60 s al insertar. Nada se persiste ni sale del daemon (SEC-04: ni argv ni entorno). **La reclamación se inserta antes de responder al hook**, mientras el `git` espera | A: el recorrido y `nearest_git` solo se hacen si la decisión es `allow`, hay alguna `refs/heads/*` con oid nuevo **y el detector tiene alguna sesión viva en el repo** (consulta barata): sin sesión no hay nada que atribuir y se evita el coste de `presence()` con un multiplexor. C: tope y caducidad con prueba de inundación (`claims_are_bounded`) |
| S4-4 | **Correspondencia con el evento**: para un evento `commit`, `merge`, `rebase`, `branch-update` o `branch-create` con `branch` y `new_commit`, el detector busca una reclamación del mismo `repo_id`, `refname = refs/heads/<branch>`, **mismo oid anterior** (`old_commit`; una reclamación sin oid anterior solo casa con un evento sin él) y mismo oid nuevo, con `t ∈ [t_recv − 5 s, t_flush]`, cuyo worktree (prefijo más largo de los observados) es el del evento, y cuya sesión está **presente** en el repo. Exactamente una sesión → `Attributed` con evidencia `{"signals":["s4"]}`; varias → se sigue con S3. La reclamación usada **se consume** (una operación, un evento). `branch-switch`, `push`, `reset` y la reconciliación nunca usan S4. La ventana empieza 5 s antes de `t_recv` porque el aviso de `objects/` puede abrir el lote antes del `prepared` y la reclamación puede llegar después de `t_recv`; lo cubre igualmente | A: casar también el oid anterior, porque S4 gana a un `git` ajeno visto por S3 y tiene que probar que es **ese** movimiento |
| S4-5 | **Precedencia**: S4 se mira antes que S3 (ya era así en `Detector::evidence`): prueba qué `git` escribió esa ref con ese oid, aunque S3 vea a la vez un `git` ajeno en el repo (GitKraken). Sin sesión presente en el repo, `NoSession` como hoy | |
| S4-6 | **Revocación**: si la segunda línea (`commit` `second-line`) del mismo `git` (pid, inicio) deniega, sus reclamaciones se retiran: la ref no se moverá | A: es una protección parcial (si la llamada de la segunda línea falla, o Git u otro hook abortan después de `prepared`, el daemon no se entera). La protección real es la combinación de ref, oids, worktree, ventana y consumo. Revisor: además, **todo movimiento permitido posterior de la misma rama retira sus reclamaciones anteriores**, sea de quien sea, para que una reclamación huérfana (transacción abortada) no le dé al agente el `reset` del desarrollador al mismo commit |
| S4-7 | **Sin hooks, nada cambia**: sin `guard.evaluate` no hay reclamaciones y `evidence` sigue el camino de hoy (S3, registro, pista). El log `s3_evidence` gana el resultado `s4` para medir en SPIKE-GRP-001 | |
| S4-8 | **Costura**: `HookEvidence`/`NoHooks` (D9 de esta Dev Spec, `session_for(repo, worktree, t_recv)`) se sustituye por `HookClaims` concreto, que `Detector::start` recibe; `Detector::evidence` gana el movimiento de rama del evento (`RefMove`) y `S3Outcome` gana `Hook`. Sin reclamaciones, `HookClaims` vacío se comporta como `NoHooks` | A: declarar el cambio de firma |

**Pruebas**:

- `crates/core/src/detect/hook.rs`: reclamación de un agente y consumo; el evento tiene que ser el mismo movimiento (rama, oid anterior y nuevo, repo, ventana, worktree); sin prueba de agente no hay reclamación (`git` del desarrollador, `deny`/`ask`, sin sesión viva en el repo, etiqueta, borrado); **Claude Code y el `git` del desarrollador en el mismo tmux: sin S4**; **el `git` del propio daemon: sin espera y sin S4**; revocación y caducidad; tope.
- `crates/core/src/detect/tests.rs`: S4 atribuye con un `git` ya terminado (sin muestras) y se consume; worktree del evento (prefijo más largo), sesión ausente, dos sesiones y fuera de ventana → decide S3; sin movimiento o sin sesión no se lee.
- `apps/cli/tests/events_s4_hook_attribution.rs` (macOS, binario real como daemon y hook, repo y perfil temporales): con Guardrails instalado, un commit rápido (`git commit -qm`, sin hook lento) del Claude Code simulado sale `agent / claude-code / detected` con evidencia `{"signals":["s4"]}`; un commit del desarrollador con la sesión viva sale "sin atribuir" (también en su propio test, `a_developers_commit_next_to_a_live_agent_session_stays_unattributed`, C); sin Guardrails, el commit rápido nunca lleva evidencia `s4`. Medición `#[ignore]` (`measure_quick_commit_attribution`) que cuenta los commits rápidos atribuidos con y sin hooks, para SPIKE-GRP-001.

**Riesgos y pendientes**:

- **Linux y Windows**: S4 depende del canal (Unix) y de la detección (macOS y Linux); el e2e corre en macOS. Pendiente: etapa de validación multiplataforma.
- **Agente que mueve una rama a un oid que ya existía** (`git branch -f`, `reset` que mueve la rama) y, dentro de la ventana de 5 s, el desarrollador mueve la misma rama al mismo oid: lo evita el consumo de la reclamación salvo que el evento del agente no llegue a registrarse. Riesgo residual aceptado, medido en la suite del spike.
- **Falsos negativos aceptados** (el evento queda como sin S4, nunca mal atribuido): un `branch-update` que agrupa varios movimientos (repo sin reflog, o `git am` / dos commits seguidos dentro de la misma ventana del observador), porque su oid anterior no es el de ninguna transacción; `update-ref` o `branch -f` sin oid anterior; `git worktree add -b`, cuyo hook corre en el worktree principal; y un worktree recién creado que el detector todavía no conoce.
- **Coste**: con una sesión presente en el repo, una transacción del desarrollador bajo un multiplexor recorre los procesos del usuario (`presence()` del solicitante) mientras el `git` espera. Sin sesión presente no se hace el recorrido. Medir el p95 queda pendiente (SPIKE-GRP-001).
- **Hooks de plantilla 1**: también dejan S4 (el `reference-transaction` es obligatorio desde la plantilla 1); la segunda línea (revocación) solo existe en la 2.

## Enmienda 2026-10-08 — Detección de sesiones en Windows

Cierra el pendiente de Windows de D3. **Decisión del orquestador (2026-10-08), validada por el coordinador** (lectura del cwd por el PEB con derechos mínimos, solo procesos del mismo usuario, WOW64 rechazado, fail-closed).

| Tema | Resolución |
|---|---|
| Lista de procesos (S1) | `SystemProcLister` en Windows sobre `gitraptor-winsys`: una sola instantánea de ToolHelp por escaneo (`current_user_processes`), solo procesos del usuario actual, sin SYSTEM; `exe` solo bajo demanda (`image_of`, `QueryFullProcessImageNameW`). Identidad `(pid, hora de creación)`: la hora de creación (100 ns) se guarda en microsegundos como en las otras plataformas y se compara al microsegundo mientras se lee cada dato |
| Identificar a Claude Code | **La ruta de la imagen resuelta por el kernel**, nunca la línea de comandos (SEC-04): `AgentMatcher::classify` es el mismo en los tres SO (`claude`/`claude.exe` por nombre de archivo, carpeta `claude\versions\<versión>`, paquete npm `@anthropic-ai\claude-code`; el nombre sin distinguir mayúsculas). Un binario copiado y llamado `claude.exe` se acepta igual que en macOS y Linux: es el hueco declarado de S1 (la identidad por ruta no es una firma) |
| cwd de otro proceso | `winsys::process::cwd(pid, creación)`: `NtQueryInformationProcess(ProcessBasicInformation)` → PEB → `RTL_USER_PROCESS_PARAMETERS.CurrentDirectory.DosPath`, con `ReadProcessMemory` de **tres trozos pequeños** (el puntero a los parámetros, el `UNICODE_STRING` y el texto, con tope de 32 768 unidades), **nunca `CommandLine` ni `Environment`**. Derechos mínimos (`PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_VM_READ`, solo para esa llamada); el proceso debe ser del usuario actual, comprobado en su token antes de leer memoria; un proceso de 32 bits (WOW64) se **rechaza**, no se adivina; la hora de creación se comprueba antes y después. **No legible = desconocido, nunca "no es un agente"**: todo fallo (elevado, protegido, otro usuario) es `Denied` y el llamante deja al proceso en duda. Lo que el proceso escribe en su propio PEB es **dato hostil**: solo se acepta una ruta de unidad (`X:\…`) de componentes planos (sin UNC ni de dispositivo, sin `/`, `.`, `..`, ni componentes que acaben en punto o espacio) cuya unidad sea un **disco fijo local** (`GetDriveTypeW`); cualquier otra cosa es desconocida. Solo entonces el detector resuelve los enlaces de la ruta (`canonicalize`) y la compara con las de los worktrees (forma de unidad, sin `\\?\`). La hora de creación del último escaneo ata el cwd a ese proceso aunque Windows reutilice el pid |
| Mismo cwd para el log de Guardrails | `channel::peer::process_cwd` lo usa en Windows: sin él `raptor guard log` salía vacío porque el demonio no sabía en qué repo corría el hook |
| `detection_supported()` | Verdadero en Windows: `sessions.list` ya no devuelve `detection_available: false`, y `raptor status`/`sessions`/`timeline` dejan de decir "no se puede detectar" |
| Intérpretes | Sin cambio: Claude Code instalado por npm (`node …\cli.js`) no se detecta (no hay lectura acotada de `argv[1]`); no da falsos positivos |

**Pruebas** (Windows): `winsys` (`process::tests`: cwd de un hijo, de este proceso, hora de creación distinta → `Gone`, 32 bits rechazado, otro usuario y System nunca leídos, la lista y `image_of`, formas de ruta), `core` (`detect::procs::windows_tests`, `channel::authz::classifier_table_on_windows_paths`) y `apps/cli/tests/claude_sessions_windows.rs` (el `raptor` real como demonio y cliente: un `cmd.exe` copiado como agente conocido, en un worktree de una ruta con espacios, aparece como "Claude Code · Active · detected" y al terminar queda `ended` con `process-gone`; un proceso con otro nombre no es sesión; un agente fuera de todo worktree observado tampoco). Con el binario release y un `claude.exe` copiado, en la máquina real: `raptor status` lo muestra activo y luego terminado.

**Revisión de seguridad (2026-10-08)**: sin críticos; el alto (H-01: la ruta leída del PEB se abría con `canonicalize`: UNC, rutas de dispositivo y letras redefinidas por el proceso) y los hallazgos M-02 (cwd atado a la hora de creación) y L-01 (componentes con punto o espacio al final) están corregidos aquí. **Quedan abiertos**: M-01 (el `canonicalize` del cwd corre con el cerrojo del detector; con solo discos fijos el bloqueo es improbable, pero conviene calcular los cwd antes del cerrojo como hace `sample()`), I-01 (contar en el diagnóstico los procesos cuyo token no se lee) e I-04 (`list()` lee la imagen de todos los procesos cuando solo hacen falta los `git`). Riesgo residual aceptado (I-02): un proceso del mismo usuario cuya imagen se llame `claude.exe` es una sesión, como en macOS y Linux. Modelo de amenazas por decidir: procesos de baja integridad o AppContainer con el mismo SID cuentan como del usuario actual.

**Pendiente**: medir el coste del escaneo por segundo en Windows (RES-01 en la etapa de validación); S3 (atribución de commits por ascendencia) sigue la misma regla que en macOS pero no tiene su e2e en Windows; Windows 11.
