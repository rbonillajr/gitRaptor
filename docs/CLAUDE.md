# GitRaptor — AADD Context Rules

This directory is an AADD domain (orchestration layer active). Obey these rules
when answering any question about the domain or editing any artifact within it.

<!-- aadd:orchestration-contract v1 -->
## 0. Orchestrate — delegate, don't produce (read first)

You (the orchestrating agent) ORCHESTRATE this domain; you do **not** produce phase
artifacts in your own context:

- **Delegate each phase via its `/aadd-*` command** (each loads the right specialized
  subagent + canonical template): requirement → `/aadd-specify` (PO; stops at the human
  checkpoint), user stories → `/aadd-stories` (PO, after you approve the requirement in
  natural language, e.g. "apruebo el requerimiento de <feature>"), design → `/aadd-design`
  (UX), architecture & dev specs → `/aadd-architect` / `/aadd-devspec`, planning →
  `/aadd-plan` (SM).
- **Never hand-write** `context.md`, a user story, an ADR, a Tech Story, or a Dev Spec
  yourself. If you start to, STOP and delegate.
- **Respect the gates** (enforced, not advisory): the requirement→stories human approval
  gate, the format-check hooks, and the Artifact Judge.
- **When lost** about the phase or next step, ask the `aadd-guide` coach — don't guess.
<!-- /aadd:orchestration-contract -->

## 1. Consult memory BEFORE answering

For ANY question about the domain — architecture, decisions, stories, specs,
"why is X this way", "what did we decide about Y" — run FIRST:

```
/aadd-recall "<2-5 keywords from the user question>"
```

Use the top-5 results as your factual grounding. Cite artifact IDs inline
(e.g., "per ADR-GRP-003 and TS-GRP-012..."). Never answer from
generic assumptions when the memory might have a prior decision.

Skip memory lookup only for pure coding tasks that never touch architecture
(e.g., "fix a typo in this regex").

## 2. Canonical IDs

Artifacts in this domain follow `<TYPE>-GRP-NNN`:
- ADRs → `ADR-GRP-*`
- User Stories → `US-GRP-*` (or per-feature slug: `US-REC-*`, `US-PRA-*`, ...)
- Tech Stories → `TS-GRP-*`, `TD-GRP-*`, `INF-GRP-*`, `SPIKE-GRP-*`
- Dev Specs → `DS-<STORY-ID>`
- Design Flows → `DSF-GRP-*`
- Design Specs (visual handoff, optional) → `DSG-GRP-*`

Never invent an ID. New artifacts MUST continue the numeric sequence for their
(type, slug) pair. Check `ARTIFACTS.md` for the current max.

## 3. Frontmatter is mandatory

Every `.md` artifact starts with a YAML frontmatter block per
skill `aadd-framework` → `references/artifact-frontmatter-schema.md`.
When creating or migrating an artifact, always emit the canonical frontmatter first.

## 4. Files that ARE catalogs, not artifacts

- `ARTIFACTS.md` — auto-generated. **Do not edit by hand.** Regenerated by
  `/aadd-index` or by the PostToolUse auto-touch hook.
- `analyze-report.md` — auto-generated by `/aadd-analyze`. Audit only.
- `.aadd/memory.json` — auto-generated inverted index. Gitignored.
- `user-stories.md`, `technical-stories.md` at feature level — INDEX files (table only).
  Real stories live in sibling `user-stories/` and `technical-stories/` directories,
  one file per story. The `design/` directory holds `design-flow.md` (always) and the
  optional `design-spec.md` (visual handoff).

## 5. Closing a feature

When a feature ships, run:
```
/aadd-archive --feature <feature-name> --release "<tag>"
```
This snapshots the working set into `archive/YYYY-MM-DD-<feature>/` with a
CHANGELOG delta. Do not keep `rev-N/` folders.

## 6. Before PR

Run the consistency gate:
```
/aadd-analyze --strict
```
Fix any BLOCKER before merging. CONCERNS may pass with reviewer approval.

## 7. Handy shortcuts

| Goal | Command |
|------|---------|
| "What did we decide about X?" | `/aadd-recall "X"` |
| List everything in the domain | open `ARTIFACTS.md` |
| Refresh catalog + memory manually | `/aadd-bootstrap --apply --skip-migrate` |
| Spawn a new feature | `/aadd-specify <feature>` |
